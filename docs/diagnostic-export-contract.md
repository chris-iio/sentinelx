# Diagnostic Export Contract

## Reader and action

This document is for the engineer implementing the next diagnostic export slice. After reading it, they should be able to gather diagnostic sources and build a manifest that records every source outcome without leaking provider secrets or introducing a download route prematurely.

## Scope

S01 defines the backend-only manifest vocabulary for a future diagnostic export. It does not gather files, assemble archives, expose a route, or read local planning/runtime directories. The contract is intentionally small and deterministic so later code can use it from service logic, tests, or route handlers without importing web handlers.

## Manifest version

The initial manifest schema version is:

```text
diagnostic-export-manifest/v1
```

Every serialized manifest includes this value. Breaking changes require a new version string; additive optional fields can remain on the same version if old consumers can ignore them safely.

## Source classes in scope for S02

S02 may represent these source categories in the manifest:

- `health` — secret-free health and readiness payloads.
- `orchestrator` — bounded enrichment job/provider diagnostic counters.
- `cache` — cache summaries or bounded excerpts, never unbounded raw cache dumps.
- `history` — analysis/history summaries or bounded excerpts.
- `config` — configuration shape and provider enablement metadata, never stored provider key values.
- `runtime` — supported runtime state needed to debug the local development loop.
- `metadata` — bundle metadata generated by the exporter itself.

A source record must have a stable `source_id`, human-readable `name`, `category`, and explicit `status`. At least one location/display field must identify what the source represents: a relative path, display path, or logical label.

## Source statuses

A manifest must not silently drop a source attempt. Every source considered by the exporter must serialize as one of these statuses:

| Status | Meaning | Required handling |
|---|---|---|
| `included` | The source was collected fully within its byte bound. | Record original and included byte counts. |
| `truncated` | The source was collected partially because it exceeded its byte bound. | Record original bytes, included bytes, max bytes, and `truncated: true`. |
| `omitted` | The source was intentionally skipped. | Record an `omitted_reason`; the default is `not_collected`. |
| `error` | The source was attempted but could not be collected. | Record a bounded `safe_error_summary`; do not include stack traces, raw paths with secrets, or secret values. |

Invalid status or category values are rejected instead of producing ambiguous manifests.

## Bounds and deterministic serialization

Default per-source maximum size is `256 KiB`. S02 can choose tighter source-specific bounds, but it should enforce them before bytes enter an archive. Source metadata operations are expected to be O(number of sources + metadata size), not proportional to raw bundle size.

The manifest includes aggregate counts for:

- total sources
- included sources
- truncated sources
- omitted sources
- errored sources
- redaction events

Serialization is JSON-safe and deterministic:

- No wall-clock value is generated inside the contract. Callers may pass a timestamp.
- Source records are sorted by `source_id` when serialized in a manifest.
- JSON helpers emit stable key ordering.
- Missing optional location fields serialize to `null`, except a missing source label falls back to the source name so readers still have a displayable label.

## Redaction-before-export rule

Redaction must happen before any source bytes are handed to an archive or download response. The manifest can report `redaction_count` and stable `redaction_labels`, such as `api_key` or `token`, but it must never include the redacted secret value or enough surrounding context to reconstruct it.

Recommended S02 order of operations:

1. Read or derive the source under the source-specific byte policy.
2. Redact secret values and record redaction labels/counts.
3. Apply truncation limits to the already-redacted bytes.
4. Emit an `included`, `truncated`, `omitted`, or `error` source record.
5. Serialize the manifest after all source outcomes are known.

## Safe error summaries

Error summaries are bounded to 120 characters and normalized to a single line. They should describe the failure class and source, for example:

```text
PermissionError while reading history store
```

They must not include stack traces, raw secret-bearing configuration, request headers, API keys, tokens, or full user input.

## Non-goals for S01

S01 deliberately does not provide:

- a diagnostic download route
- zip or bundle assembly
- filesystem traversal
- reads from local planning/runtime directories
- runtime observability signals
- secret discovery beyond manifest redaction counters and labels

Those behaviors belong to later slices and should build on this contract rather than changing it ad hoc.
