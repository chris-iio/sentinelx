# Diagnostic Export Contract

## Reader and action

This document is for the engineer implementing or reviewing SentinelX diagnostic export work. After reading it, they should be able to assemble backend diagnostic sources into a deterministic bundle, inspect the manifest for every source outcome, and know which route/UI responsibilities still belong to the next slice.

## Scope

The diagnostic export is a local-first troubleshooting bundle for the SentinelX app. Its backend contract covers three things:

1. A stable manifest vocabulary for source outcomes.
2. Redaction-before-export rules for source payloads and error summaries.
3. Deterministic archive assembly from explicitly supplied diagnostic sources.

The backend contract does not itself expose a download route, add UI controls, upload logs, read planning directories, or ship telemetry. Route headers, response errors, and analyst-facing download affordances remain the responsibility of the route/UI slice.

## Manifest version

The manifest schema version is:

```text
diagnostic-export-manifest/v1
```

Every serialized manifest includes this value. Breaking changes require a new version string; additive optional fields can remain on the same version if old consumers can ignore them safely.

## Source categories

A source record must have a stable `source_id`, human-readable `name`, supported `category`, explicit `status`, and at least one displayable identifier: archive-relative path, display path, or logical label.

Supported categories are:

- `health` — secret-free health and readiness payloads.
- `orchestrator` — bounded enrichment job/provider diagnostic counters.
- `cache` — cache summaries or bounded excerpts, never unbounded raw cache dumps.
- `history` — analysis/history summaries or bounded excerpts.
- `config` — configuration shape and provider enablement metadata, never stored provider key values.
- `runtime` — supported runtime state needed to debug the local development loop.
- `metadata` — bundle metadata generated by the exporter itself.

Invalid status or category values are rejected instead of producing ambiguous manifests.

## Source statuses

A manifest must not silently drop a source attempt. Every source considered by the exporter must serialize as one of these statuses:

| Status | Meaning | Required handling |
|---|---|---|
| `included` | The source was collected fully within its byte bound. | Record original and included byte counts. |
| `truncated` | The source was collected partially because it exceeded its byte bound. | Record original bytes, included bytes, max bytes, and `truncated: true`. |
| `omitted` | The source was intentionally skipped. | Record an `omitted_reason`; the default is `not_collected`. |
| `error` | The source was attempted but could not be collected. | Record a bounded `safe_error_summary`; do not include stack traces, raw paths with secrets, or secret values. |

Source failures are isolated. A failing history, cache, config, health, or optional orchestration source should become an `error` record and must not abort unrelated sources. Caller contract violations, such as duplicate source IDs or unsafe archive paths, fail the whole assembly before any source is collected.

## Backend archive contract

The backend assembler returns archive bytes, the parsed manifest object, the stable archive path list, and a secret-free summary with aggregate counts and archive size.

Archive assembly is deterministic when callers provide the same inputs and timestamp:

- `manifest.json` is always present.
- Source entries use stable archive-relative paths.
- Source records are sorted by `source_id` in the manifest.
- Payload entries are sorted by archive path.
- ZIP metadata uses a fixed timestamp and stored compression.
- JSON payload serialization uses stable key ordering.

The archive must not contain entries outside the diagnostic bundle namespace. Absolute paths, parent traversal, Windows drive paths, backslash paths, `manifest.json` collisions, and planning/runtime control directories are rejected.

## Bounds and serialization

The default per-source maximum size is `256 KiB`; runtime source composition may choose tighter bounds. Truncation is per source, after redaction, and reflected in both source-level byte counts and aggregate manifest counts.

The manifest includes aggregate counts for:

- total sources
- included sources
- truncated sources
- omitted sources
- errored sources
- redaction events

Serialization is JSON-safe and deterministic:

- No wall-clock value is generated inside the manifest contract. Callers pass a timestamp.
- Missing optional location fields serialize to `null`, except a missing source label falls back to the source name so readers still have a displayable label.
- Unserializable source values are represented by safe type-name placeholders, not by object `repr()` values that might leak secrets.

## Redaction-before-export rule

Redaction must happen before any source bytes are written to an archive or returned from a download response. The manifest can report `redaction_count` and stable `redaction_labels`, such as configured-secret or bearer-token labels, but it must never include the redacted secret value or enough surrounding context to reconstruct it.

Backend assembly order:

1. Validate all source descriptors and archive paths before collecting any source.
2. Collect one source payload or mark it intentionally omitted.
3. Redact the payload or error summary.
4. Encode the redacted payload as bytes.
5. Apply the source byte limit.
6. Emit an `included`, `truncated`, `omitted`, or `error` source record.
7. Serialize the manifest after all source outcomes are known.

Configuration inventory is label-only. It may report which providers have configured secrets and how many are present, but it must not export the stored provider key values.

## Safe error summaries

Error summaries are bounded to 120 characters and normalized to a single line. They should describe the failure class and source, for example:

```text
PermissionError while reading history store
```

They must not include stack traces, raw secret-bearing configuration, request headers, API keys, tokens, or full user input. Bearer-token-like prose must be redacted even when it appears in exception text.

## Runtime source composition

Default backend runtime source composition is dependency-injected. Callers explicitly provide the stores, health checks, optional job ID, and optional job diagnostics accessor they want considered.

The default source inventory includes:

- diagnostic export metadata
- configuration secret inventory
- cache statistics
- recent history summaries
- history-save diagnostics
- health and dependency checks
- optional orchestration diagnostics

Missing optional runtime objects are represented as `omitted` records with explicit reasons. Failing runtime objects become `error` records. Recent history is bounded by the default history limit even if a caller asks for more.

## Route boundary

The backend assembly slice intentionally leaves these routes unavailable:

```text
/diagnostics/export
/api/diagnostics/export
```

The route/UI slice is expected to replace this negative boundary with positive route-level tests that prove:

- the supported route returns a diagnostic archive with safe headers
- route errors are bounded and secret-free
- the archive still contains no provider secrets
- the UI gives analysts concise guidance for generating and sharing the bundle

## What S01 and S02 prove

S01 proves the manifest and redaction primitives: source records, manifest serialization, redaction metadata, safe error summaries, and route absence.

S02 proves backend assembly and runtime composition: deterministic ZIP output, per-source bounds, redacted payloads and error summaries, omitted/error records for missing or failing runtime dependencies, safe archive path validation, dependency-injected runtime source collection, and continued route absence.

## Non-goals before the route/UI slice

The backend slices deliberately do not provide:

- a diagnostic download route
- a visible UI button or analyst workflow
- remote upload or log shipping
- filesystem crawling
- reads from planning or audit directories
- long-term log retention
- multi-user access control

Those behaviors require separate route-level and UX proof rather than ad hoc changes to the backend contract.
